# Software Factory

Run one repo-local development job from durable files. The job record is the handoff between sessions; chat history is never required to resume. Read [job format](../../../factory/job-format.md), [roles](references/roles.md), and [model policy](references/model-policy.md) before intake or resumption. Copy the appropriate [templates](assets/) into the job directory as stages begin. Follow the user's repository Git instructions as well as this skill.

## Entry paths

- `$software-factory new <request>`: create a unique filesystem-safe job ID and a frozen `task.md` from [task template](assets/task.md). Record the target repo and exact starting SHA. If the request lacks an outcome-defining fact, ask a focused question and do not invent acceptance criteria.
- `$software-factory resume <job-id>`: find `factory/jobs/<job-id>/` on its checkpoint branch/worktree. Read `task.md`, `state.json`, `history`, artifacts, and Git refs; validate before acting. Use the stage and records, not the prior chat, to decide the next step. Do not alter a frozen packet. A changed criterion starts a new versioned job from the same baseline, with the reason in its new packet.
- A user can select `solo` or `team`. The comparison holds packet, baseline, checks, model settings, and review gate constant. Record the mode and actual model/effort of every run. If subagents are unavailable in team mode, stop with `NEEDS-HUMAN` or explicitly start a separately labeled solo run; never silently relabel the team run.

## Intake and ownership

1. Confirm the main checkout is clean: `git status --porcelain=v1` must print nothing. Run `git fetch origin --prune`, inspect `git log --oneline --decorate -5 main origin/main`, and require `git rev-parse main` to equal `git rev-parse origin/main`. Stop on divergence or unexpected commits.
2. Choose the next unused checkpoint number and a short name. Create `codex/checkpoint-<number>-<short-name>` from synchronized `main`. Prefer the Codex worktree tool. If its checkout is not writable, use `git worktree add -b <branch> <path> main` in an allowed, ignored location (or `git worktree add <path> <branch>` if the branch was already created). A running job's files and changes stay in that worktree. Confirm its `git rev-parse HEAD` equals the recorded baseline. If isolation is blocked, stop and report it rather than treating a shared dirty checkout as an isolated run.
3. Create `factory/jobs/<id>/task.md` from the task template and choose `baseline`, `workflow_commit` (the workflow instructions commit), requested `model_profile`, `mode`, branch, and initial `null → intake` history entry. The task's exact checks include `git diff --check`. See [job format](../../../factory/job-format.md) for the complete state shape.
4. Generate a unique owner ID for this orchestration session. Run `python3 tools/job_io.py claim factory/jobs/<id> <owner-id>` **before writing state**. If it fails, report the conflict and stop. A missing or damaged claim is not permission to take over an abandoned run; require explicit human resolution. Never infer staleness from time. Write the initial state through the helper in step 5, then commit the frozen packet and initial state before assigning roles.
5. For each state change, build a candidate JSON file, run `python3 tools/job_io.py write-state factory/jobs/<id> <owner-id> <candidate-json-file>`, then `python3 tools/validate_job.py factory/jobs/<id>`. The helper validates and replaces state atomically. Only this orchestrator writes `state.json` and `decision.md`.

## Stage loop

- **Spec:** Give the spec writer `task.md`, relevant repository files, and [spec template](assets/spec.md). In solo mode, the same agent can also build; record the dual role. The writer creates only `spec.md`. Clarify behavior, edge cases, affected boundaries, and observable criteria without silently changing the requested outcome. A consequential scope change becomes `NEEDS-HUMAN`.
- **Build:** Give the builder only the frozen packet, accepted spec, relevant repository context, and [build template](assets/build.md). The builder alone changes product code, commits reviewable changes, runs every task-declared check, and writes `build.md` with commands, exit status, output, and commit SHA. An agent's claim of success is not check evidence. The orchestrator records exact check evidence in state.
- **Review:** Code review is always assigned. Assign security review when credentials, permissions, untrusted input, dependencies, or other security-sensitive behavior changes. Assign UI review for user-facing interfaces. Independent reviewers read the same spec, diff, and checks. Run them in parallel only when their separate report files prevent write conflict. Each writes only `reviews/round-N/<role>.md` from [review template](assets/review.md), starting with `VERDICT: PASS` or `VERDICT: CHANGES`, concrete findings, severity, and file references. Builder self-review never replaces independent code review.
- **Repair:** Wait for every assigned report in the round before deciding. If any says `CHANGES`, consolidate findings and return them to the *same* builder. After repair, rerun applicable checks and reviewers affected by changed code. Use a new round directory. Allow at most two repair cycles; an unresolved important finding, missing reviewer, or failed/unavailable required check cannot yield `READY`. After cycle two, record `NEEDS-HUMAN` or `FAILED` with a recovery path.
- **Decision:** Write [decision template](assets/decision.md) with `DECISION: READY`, `DECISION: NEEDS-HUMAN`, or `DECISION: FAILED`, reasons, and evidence links. A task check that proves inapplicable closes this run; create a revised packet as a new run. Write and validate the terminal state. Release the claim with `python3 tools/job_io.py release factory/jobs/<id> <owner-id>` after the terminal records are committed. A `READY` decision means eligible for delivery, not merged.

Validate after every transition. The permitted transitions and review gate are in [job format](../../../factory/job-format.md). Record human questions/answers, model/effort deviations, start/end times, usage if exposed or `null`, and artifact paths. For job files, commit stage artifacts in focused commits; the builder's product changes and review fixes remain distinguishable.

## Delivery gate

After all reviews, write `decision.md` and the final `READY` state, validate the job, and commit those records with every review report on the checkpoint branch. Run the full applicable local gate, including `python3 -m unittest discover -s tests -v` for this repo and `git diff --check`; record command, exit code, and relevant output. Request independent review of the complete branch. Fix all Critical and Important findings and re-review those fixes. Do not push until records, tests, and review are committed and the branch is clean.

Fetch and inspect remote state, then push the checkpoint branch and confirm `git rev-parse HEAD`, `git rev-parse origin/<branch>`, and `git ls-remote origin refs/heads/<branch>` are the same SHA. Wait for the human merge decision for this job. Immediately before merge, fetch again, require a clean `main` checkout, and confirm `git rev-parse main` equals `git rev-parse origin/main`; stop on any unexpected change. Merge with `git merge --no-ff <branch>`, rerun the applicable gate, push `main`, and confirm local, tracking, and remote main SHAs match. Preserve the checkpoint branch.

Only after that verified merge, create a **new** annotated `factory/<job-id>` tag pointing to the merge commit. Its message records job ID, selected branch tip, and verification summary. Push it and confirm the remote peeled tag SHA equals the merge commit. If the tag already exists, stop and inspect it; never replace it. The tracked job record ends at `READY`; Git refs and this tag supply delivery status. Do not report a job fully complete without the record, synchronized refs, and matching remote tag.
